# 다중 문서와 저장 복구 구현 계획

현재 진행중: 계획 2단계까지 확인 완료 후 구현중

2026년 10월 20일 정리

한 창에서 여러 그림을 열고, 문서별로 저장과 복구를 끝까지 이어가는 계획이다.
1단계 상태 분리, 2단계 탭, 3단계 문서별 복구, 4단계 파일 연결을 구현 단위로 정한다.
문서 닫기와 앱 종료의 저장·저장하지 않음·취소 확인 흐름은 이번 완료 범위에서 제외하고 후속 구현으로 남긴다.
아래 자료형과 표, 검사 항목은 목표 명세다. 현재 구현을 뜻하지 않는다.
체크가 없으면 아직 완료가 아니다. 날짜나 자료형 이름만으로 완료를 약속하지 않는다.

## 범위와 완료 기준

- [ ] 문서마다 그림과 실행 취소, 화면 상태를 따로 가진다.
- [ ] 새 그림과 파일 열기는 기존 그림을 바꾸지 않고 새 탭을 만든다.
- [ ] 문서마다 다른 복구 파일에 저장하고 강제 종료 뒤 각각 복구한다.
- [ ] 복구한 그림을 유지하면서 유효한 원본 연결만 복원한다.
- [ ] 원본 저장과 복구 저장의 완료 상태를 따로 표시한다.
- [ ] 늦게 끝난 작업이 다른 문서나 이미 닫힌 문서를 바꾸지 않는다.
- [ ] 기존 파일 읽기와 손상된 저장의 이전 세대 복구를 유지한다.
- [ ] 문서 수, 보관 버퍼, 저장 대기열에 상한을 둔다.

한 창의 탭만 만든다. 여러 창, 창 사이 탭 이동, 문서 간 레이어 이동은 제외한다.
타일 엔진, 변경분 로그, 주기적 체크포인트, 저장 형식의 청크 분리는 후속 작업이다.
이 범위의 그림 본체는 기존 v9 전체 스냅샷을 사용한다. 실행 취소 이력은 디스크에 저장하지 않는다.
새 메타데이터는 그림 본체와 분리하며 기존 `Document`에 UI나 파일 경로를 넣지 않는다.

정상 종료 뒤에는 저장된 채 열려 있던 탭을 원본에서 다시 연다. 미저장 탭은 보관한 복구본에서 복원한다.
비정상 종료 뒤에는 유효한 복구본을 우선한다. 원본 읽기는 복구 그림을 교체하는 동작이 아니다.
명시적으로 닫은 문서는 다음 실행에서 자동으로 되살리지 않는다. 후속 구현에서 명시적으로 버린 문서에도 같은 규칙을 적용한다.
아직 편집하지 않은 빈 새 문서는 확인 없이 닫고 재시작 목록에도 남기지 않는다.

## 현재 출발점

1A 상태 추출을 반영했다. `Parfait`의 `DocumentManager`는 현재 `DocumentSession` 하나를 소유한다.
그림·History·뷰·편집·레이어 UI·원본/복구 상태는 세션에만 있고, 표시 캐시는 `WindowRenderCache`에 있다.
문서/세션 키로 캐시와 위젯·명령·편집 초안을 구분하지만 다중 탭이나 영속 세션 목록은 아직 없다.
`project_state.rs`의 열기는 현재 그림을 교체한다. 파일 경로와 원본 저장 기준은 메모리에만 있다.
앱을 열면 고정된 `recovery.parfait`를 읽고 `project`와 `project_saved_state`를 None으로 시작한다.
현재 작업 트리에는 복구본의 원본 경로 메타데이터를 저장하는 코드가 없다.

`parfait-storage`는 문서 전체를 직렬화하고 해시와 zlib 압축 뒤 SQLite에 기록한다.
최대 최근 3개 revision의 스냅샷을 남긴다. 작업자의 대기 슬롯은 문서 구분 없이 하나다.
`mark_clean()`은 해당 데이터베이스의 정상 종료 표시다. 원본 저장이나 복구 파일 삭제를 뜻하지 않는다.
일반 파일 저장은 동기 처리다. 종료는 복구 저장을 마무리하지만 원본 변경 확인은 하지 않는다.

## 공통 규칙

1. 그림 내용, 편집 세션, 앱 설정, 디스크 기록을 서로 다른 자료로 다룬다.
2. 원본 파일 저장이 끝나도 그 뒤의 수정까지 저장됐다고 표시하지 않는다.
3. 저장 응답은 현재 탭이 아니라 요청을 만든 문서에 적용한다.
4. 탭 전환과 확대, 활성 레이어 선택은 새 그림 편집 상태를 만들지 않는다.
5. 선택 범위의 실제 변경은 기존 동작처럼 그림 편집 상태에 포함한다.
6. 경로가 없거나 읽기에 실패하면 활성 원본 연결은 None으로 둔다. 복구 그림은 남긴다.
7. 실패한 열기로 기존 탭을 지우거나 실패한 저장으로 원본 연결을 먼저 바꾸지 않는다.
8. 앱이 소유한 복구와 설정 파일을 사용자 저장 대상으로 고를 수 없게 한다.
9. 파일 읽기와 원본 검증은 없는 파일이나 테이블을 생성하지 않는다.
10. 한 단계의 변경에 레이어 알고리즘과 새 그림 포맷을 함께 넣지 않는다.

## 식별자와 상태 용어

| 이름 | 의미 | 바뀌는 때 |
| --- | --- | --- |
| `DocumentId` | 복구 저장소와 탭의 안정적인 ID | 새 문서를 만들 때 |
| `SessionEpoch` | 이번 메모리 세션의 수명 식별자 | 문서 세션을 처음 만들거나 다시 메모리에 올릴 때 |
| `EditStateId` | 그림의 논리적 편집 상태 | 실제 편집을 확정할 때 |
| `revision` | 실행 중 갱신과 캐시 무효화 카운터 | 기존 문서 갱신 규칙에 따라 |
| `RequestId` | 비동기 작업의 개별 요청 | 작업을 제출할 때 |
| `BindingEpoch` | 원본 연결의 세대 | 연결을 바꾸거나 끊을 때 |
| `recovery_generation` | 복구 DB의 스냅샷 행 식별자 | 복구 커밋을 만들 때 |

`DocumentId`와 `EditStateId`는 OS 난수로 만든 128비트 값이다. 경로나 시각에서 만들지 않는다.
`DocumentSession`을 만들 때 `DocumentId`를 정하되, 새 작업 문서 생성과 기존 작업 문서 복원을 구분한다.

| 세션 생성 또는 유지 상황 | `DocumentId` | `SessionEpoch` |
| --- | --- | --- |
| 새 그림 생성 | OS 난수로 새 ID 생성 | 새로 부여 |
| 파일을 새 탭으로 열기 | OS 난수로 새 ID 생성. 원본 파일에서 세션 ID를 가져오지 않음 | 새로 부여 |
| 닫았던 파일을 나중에 다시 열기 | OS 난수로 새 ID 생성 | 새로 부여 |
| 앱 재시작으로 기존 작업 문서 복원 | 세션 저장소에 기록된 기존 ID 재사용 | 새로 부여 |
| 이미 열린 원본을 다시 선택 | 기존 탭 활성화. 세션 생성 없이 기존 ID 유지 | 기존 값 유지 |
| 같은 탭에서 다른 이름으로 저장 | 기존 ID 유지 | 기존 값 유지 |

`SessionEpoch`는 메모리 세션을 생성할 때마다 새로 부여하며 영속화하지 않는다.
따라서 복원으로 같은 `DocumentId`를 이어 써도 이전 메모리 세션의 작업 응답은 적용하지 않는다.
ID 생성 실패는 작업 실패다. 충돌을 확인하면 다시 생성하며 대체로 고정값을 쓰지 않는다.

기존 v9 그림 안의 revision과 SQLite 행 revision은 호환성 때문에 유지한다.
새 메타데이터에서는 선택한 실제 디스크 행을 `recovery_generation`으로 부른다.
손상 복구 과정에서 메모리 revision을 올리더라도 메타데이터는 원래 선택된 디스크 행에서 읽는다.
서로 다른 문서의 revision을 비교하지 않는다. 원본과 복구본의 저장 위치도 revision만으로 비교하지 않는다.

## 1단계 문서별 상태 분리

### 소유 구조

```text
Parfait
  AppSettings
  DocumentManager
    sessions
      DocumentSession A
      DocumentSession B
    tab_order
    active_document_id
  StorageCoordinator
  SessionStore
  CloseCoordinator            후속 확인 흐름 구현 시 추가
  WindowRenderCache
```

1단계에서는 `DocumentManager` 안에 세션 하나만 둔다. 화면과 명령의 의미는 바꾸지 않는다.
앱의 옛 필드와 세션 필드를 동시에 원본으로 사용하지 않는다.
이동을 돕는 접근자는 둘 수 있지만 두 군데를 갱신하는 동기화 코드는 만들지 않는다.

### 문서 세션

다음은 Rust 자료형의 책임을 나타낸다. 공개 API나 필드 배치는 구현 시 확정한다.

```rust
struct DocumentSession {
    id: DocumentId,
    epoch: SessionEpoch,
    document: Document,
    history: History,
    edit_state: EditStateId,
    binding: Option<ProjectBinding>,
    saved_baseline: Option<SavedBaseline>,
    recovery: RecoveryState,
    view: View,
    editing: DocumentEditingState,
    layer_ui: DocumentLayerUi,
    lifecycle: DocumentLifecycle,
}
```

| 기존 필드·데이터 | 새 소유자 | 규칙 |
| --- | --- | --- |
| `doc`, `history` | 문서 세션 | 다른 문서와 공유하지 않음 |
| `project`, `project_saved_state` | 문서 세션의 연결과 저장 기준 | 4단계에서 ID 기반 기준으로 전환 |
| `saved`, `submitted`, 저장 실패와 마지막 제출 시각 | 문서별 `RecoveryState` | 원본 저장 상태와 구분 |
| `stroke`, `layer_edit`, 드래그 취소 | 문서별 편집 상태 | 입력 소유 문서 ID도 확인 |
| 레이어 체크, 접힘, 이름 변경과 상세 설정 초안 | 문서별 레이어 UI | 레이어 ID와 세션 수명으로 검증 |
| 마스크 편집 대상과 오버레이 | 문서별 편집 상태 | 다른 탭으로 전달하지 않음 |
| `view` | 문서 세션 | 실행 중 탭 전환에 유지 |
| 선택 경계와 레이어 미리보기 캐시 | 활성 문서용 캐시 | 문서 키가 바뀌면 폐기 |
| 브러시, 전역 색상, 도구 설정, 필압 보정 | 앱 공통 설정 | 탭 전환으로 바꾸지 않음 |
| 단축키, 팔레트 배치, 표시 설정 | 앱 공통 설정 | 기존 preferences 저장 유지 |
| 창 상태, 도움말, 진단 캡처 | 앱 | 문서 그림과 무관 |

전체 캔버스 텍스처는 창에 하나만 유지한다. 비활성 문서마다 큰 GPU 텍스처를 보관하지 않는다.
레이어 미리보기와 선택 경계도 활성 문서용으로 시작한다. 문서 복귀 때 다시 만들 수 있다.
캐시 키에는 `DocumentId`와 `SessionEpoch`를 포함한다. revision과 LayerId만으로 구분하지 않는다.
egui 위젯 ID도 문서 ID를 포함해 같은 레이어 ID와 같은 창 이름의 포커스가 섞이지 않게 한다.

### 명령 경계

기존 메뉴, 단축키, 버튼은 동일한 명령 디스패처를 사용한다.
명령 실행 직전에 대상 문서 ID를 고정하고 세션을 조회한다. UI의 인덱스를 장기 보관하지 않는다.
그림 변경 함수에는 대상 세션을 전달하고 공통 설정은 별도 불변 참조로 준다.
레이어 코어 함수의 계산 규칙과 잠금 조건은 그대로 둔다.

`active_session_mut()`로 앱 전체를 동시에 빌리는 긴 호출 체인을 만들지 않는다.
필요한 설정값을 먼저 읽고, 대상 세션과 그릴 UI를 좁은 범위로 빌린다.
문서 명령 수행 중 활성 문서가 바뀌어도 이미 고른 대상은 바꾸지 않는다.

- [x] 문서 상태의 중복 원본 필드가 남지 않는다.
- [x] 그림, 마스크, 폴더와 선택의 합성 결과가 픽셀 단위로 같다.

## 2단계 한 창의 다중 문서 탭

### 관리자와 화면

`DocumentManager`는 ID로 세션을 찾고 별도 `tab_order`로 표시 순서를 가진다.
`active_document_id`는 세션이 있으면 반드시 유효한 ID다. 문서가 0개인 빈 작업 화면도 허용한다.
마지막 탭을 닫았다는 이유로 빈 문서를 자동 생성해 복구 파일을 다시 만들지 않는다.
시작할 때 복원할 항목이 전혀 없으면 처음 한 번 기본 빈 문서를 만든다.

탭은 문서 이름, 원본 미저장 표시, 닫기 버튼을 표시한다.
후속 확인 흐름을 넣기 전에는 미저장 문서의 닫기를 차단하고 먼저 수동 저장하도록 안내한다.
원본 파일 연결이 있으면 파일 이름을 탭 제목으로 쓰고, 없으면 `Document.name`을 쓴다.
Save As가 성공하면 `Document.name`을 저장 파일의 확장자를 제외한 이름에 맞춘다. 기존 저장 동작을 유지한다.
저장 요청의 후보 스냅샷에 새 이름을 넣고, 커밋 성공 뒤에만 해당 세션의 이름과 원본 연결을 반영한다.
실패하거나 파일 선택을 취소하면 기존 이름과 연결을 유지한다. 이름 동기화는 그림 편집이 아니라 파일 관리 메타데이터 갱신이다.
제목이 같아도 ID는 다르다. 전체 경로는 툴팁과 파일 정보 화면에서 구분한다.

저장 명령과 PNG 출력은 활성 문서가 기본 대상이다. 탭 닫기는 해당 버튼의 문서가 대상이다.
닫은 탭이 활성 탭이면 오른쪽 이웃, 없으면 왼쪽 이웃을 활성화한다.
이웃이 없으면 활성 문서를 None으로 둔다. 비활성 탭을 닫으면 활성 탭은 바꾸지 않는다.

### 새 그림과 파일 열기

1. 탭 수와 메모리 예산을 확인한다.
2. 파일 열기는 읽기 전용으로 검증하고 별도 후보 세션을 만든다.
3. 성공한 후보만 관리자에 넣는다. 실패하면 기존 탭과 활성 문서를 유지한다.
4. 입력 소유 상태를 정리하고 새 탭을 활성화한다.
5. 3단계에서는 초기 복구본과 세션 목록의 영속화까지 연결한다. 등록 실패를 탭 열기 성공과 혼동하지 않고 복구 실패로 표시한다.

새 탭의 History는 빈 상태다. 다른 탭의 History를 복사하지 않는다.
파일 읽기는 UI 밖의 제한된 작업자로 옮긴다. 로드 중 취소된 요청은 세션을 만들지 않는다.
여러 열기 요청은 사용자 요청 순서대로 탭 위치를 예약한다. 완료 순서로 뒤섞지 않는다.
사용자가 그 사이 다른 탭을 선택하면 늦은 로드 완료가 포커스를 빼앗지 않는다.

### 중복 원본 경로

이미 존재하는 파일은 정규화한 절대 경로로 조회한다. 아직 없는 저장 대상은 부모의 실제 경로와 파일명을 조합한다.
동일 원본이 이미 열려 있으면 새 탭을 만들지 않고 기존 탭을 활성화한다.
Save As 대상이 다른 탭의 연결 또는 진행 중인 저장 대상이면 거절하고 해당 탭을 안내한다.
복구 파일, 세션 DB, 설정 DB와 각 SQLite 보조 파일도 저장 대상으로 거절한다.

이 검사는 앱 안의 중복 쓰기 방지다. 하드링크, 다른 프로그램, 검사 뒤의 외부 경로 교체까지 막는 보안 경계는 아니다.
OS별 파일 식별자를 얻을 수 있으면 중복 감지에 보강하되 지원하지 않는 경우의 정책을 시험한다.
두 복구 항목이 같은 원본을 가리키면 하나만 활성 연결하고 나머지는 미연결 복구 문서로 남긴다.
자동으로 두 그림을 합치거나 한쪽을 버리지 않는다.

### 탭 전환과 입력 소유권

| 전환 전 상태 | 처리 |
| --- | --- |
| 그리는 중 | 원래 문서에서 스트로크와 History를 마무리 |
| 불투명도 등 즉시 반영 편집 | 원래 문서에서 한 번 확정 |
| 레이어 이동 미리보기 | 취소하고 실제 순서는 유지 |
| 이름 변경과 상세 설정 모달 | 확인 또는 취소 전 탭 전환 차단 |
| 저장 중 | 전환 허용, 응답은 원래 문서로 전달 |
| 문서 닫기 확정 중 | 그 문서의 변경 명령 차단 |

탭 전환 뒤 남은 pointer-up과 펜 이동을 새 그림의 스트로크로 해석하지 않는다.
다음 새 pointer-down 전까지 이전 입력 연속성을 끊는다.
한 입력 묶음에서 명령 대상이 고정되므로 A에서 시작한 편집을 B에서 끝내지 않는다.

### 메모리 예산

초기 상한은 열린 탭 8개, 열린 문서의 논리 픽셀 합 512 MiB로 시작한다.
이는 현재 문서 하나의 512 MiB 한도를 8배로 늘리지 않기 위한 입장 제한이다.
현재 문서별 4096 크기, 64개 레이어와 스냅샷 직렬화 한도도 유지한다.
정확한 기본값 변경은 별도 성능 기록과 함께 한다. 이 값은 측정한 쾌적 사용 한도가 아니다.

History, 저장 대기와 처리 중 스냅샷이 잡고 있는 고유 픽셀·마스크·선택 버퍼는 앱 전체에서 계산한다.
Arc가 같은 버퍼는 한 번만 세고 보관 픽셀 예산의 초기 상한은 1 GiB로 둔다.
새 편집의 COW 증가를 예약하고, 오래된 비활성 History부터 줄인 뒤 활성 History를 줄인다.
현재 그림과 확정되지 않은 편집의 before 상태, 실행 중 저장 자료는 임의로 해제하지 않는다.
최소 실행 취소 상태를 보존할 여유가 없으면 편집 시작 전에 거절한다. 복사 도중 예산을 넘기고 사후에 알리지 않는다.

저장 직렬화·압축 버퍼와 GPU, 스트로크 scratch는 별도다. 위 한도를 전체 프로세스 RSS로 설명하지 않는다.
동시 인코더는 하나이며 raw와 압축 결과의 최악 크기도 별도 작업 예산으로 예약한다.
예산이 없으면 요청은 대기하거나 실패한다. 다른 문서의 그림을 몰래 닫지 않는다.

### 완료 검사

- [ ] A와 B의 레이어, 선택, 마스크, 뷰와 History가 각각 유지된다.
- [ ] 같은 revision과 같은 LayerId를 가진 A와 B의 캐시가 섞이지 않는다.
- [ ] 스트로크와 드래그 중 전환이 B에 픽셀이나 순서 변경을 남기지 않는다.
- [ ] 늦은 열기 완료와 취소가 현재 포커스와 기존 탭을 덮지 않는다.
- [ ] 같은 원본 열기와 다른 탭을 대상으로 한 Save As를 검사한다.
- [ ] 탭 수와 전체 버퍼 한도에서 거절해도 기존 그림과 redo가 남는다.
- [ ] 마지막 탭 닫기와 빈 작업 화면의 명령 비활성화가 맞는다.

2단계의 탭 구현은 3단계 복구 분리가 붙기 전까지 개발 중 기능으로 둔다.
기존 단일 복구 파일에 활성 탭만 저장하는 상태를 다중 문서 완료로 배포하지 않는다.

## 3단계 문서별 복구 저장과 세션 복원

### 파일 배치

```text
<data-dir>/
  session.lock
  preferences.sqlite
  session.sqlite
  recovery/
    <DocumentId A>/recovery.parfait
    <DocumentId B>/recovery.parfait
```

문서 ID는 소문자 32자리 16진수로만 디렉터리 이름을 만든다.
세션 DB에서 임의의 복구 경로를 받아 열지 않는다. 허용된 ID로 앱이 경로를 만든다.
원본 파일 옆에 복구본을 만들지 않는다. 원본이 없거나 읽기 전용이어도 복구 저장은 독립적으로 동작한다.
기존 앱 데이터 디렉터리의 단일 프로세스 잠금을 유지한다. 다른 데이터 디렉터리의 앱까지 통제하는 잠금은 아니다.

### 세션 DB

세션 DB는 앱 설정과 별개다. 아래는 논리 스키마이며 그림 바이트를 포함하지 않는다.
경로는 현재 OS의 네이티브 단위로 인코딩하고 버전 태그를 둔다. 손실 문자열 변환을 하지 않는다.

```text
meta
  schema_version
  run_id
  clean_shutdown
  active_document_id

documents
  document_id                 primary key
  tab_order                   unique among open rows
  lifecycle                   open / closed / discarded (discarded 전이는 후속 구현)
  source_path_hint            optional encoded path
  last_recovery_generation    optional
  recoverable                 boolean

migrations
  migration_key               primary key
  target_document_id
  state                       prepared / committed
```

외래 ID와 탭 순서, lifecycle을 검증한다. 지원하지 않는 schema_version은 덮어쓰지 않는다.
현재 구현의 앱 설정 JSON에 문서 목록을 넣지 않는다. 브러시 설정 실패가 복구 목록 저장을 막지 않게 한다.
세션 레코드 전체는 초기 8 MiB, 인코딩한 경로 하나는 32 KiB로 제한한다.
문서 경로 힌트는 마지막으로 알고 있던 위치이지 원본의 신뢰 증명이 아니다.

세션 DB에 저장하는 UI는 탭 순서와 활성 문서뿐이다.
뷰, 레이어 접힘과 체크 상태는 실행 중 세션별로 유지하지만 이번 범위에서는 재시작 뒤 기본값으로 시작한다.
UI 재시작 복원을 넣으려면 그림과 별도의 버전 있는 자료형을 후속으로 추가한다.

### 복구 DB의 선택적 메타데이터

그림 payload와 user_version 9는 유지하고 다음 선택적 테이블을 추가한다.

```text
recovery_metadata
  generation                 primary key
  snapshot_checksum
  metadata_version
  payload
  metadata_checksum
```

payload는 다음 값을 가진다.

```text
document_id
edit_state_id
logical_digest_version
logical_digest
source_path                  optional
source_saved_state_id        optional
source_saved_digest          optional
source_head                  optional
```

원본 연결이 없는 것도 정상 값이다. 이전에 저장한 원본을 지워서 None이 되어도 그림은 복구한다.
메타데이터 checksum은 버전, generation, 그림 checksum과 payload를 함께 해시한다.
메타데이터는 최대 64 KiB다. 실패·손상·미지원 버전이면 연결과 저장 기준을 버리고 그림만 읽는다.
기존 형식에 메타데이터가 없으면 미연결 복구 문서로 취급한다.
경로를 포함한 전체 payload 크기를 제출 전에 검사한다. 크기 초과 경로는 활성 연결로 채택하지 않고 안내한다.
읽을 때 문서 ID가 세션 행·디렉터리 ID와 같고 상태 ID가 유효한지 확인한다.
그림에서 계산한 logical_digest가 메타데이터와 다르면 메타데이터 전체를 무시한다.
유효한 상태 ID가 없으면 새 EditStateId를 만들고 저장 기준은 모르는 상태로 시작한다.

그림 행, 메타데이터와 이전 세대 정리는 한 SQLite 트랜잭션에 넣는다.
최신 3개 그림 행에 대응하는 메타데이터만 남긴다. 같은 generation을 바꿀 때 이전 메타데이터를 그대로 두지 않는다.
구형 앱이 그림을 다시 써 checksum이 바뀌면 남은 선택적 메타데이터는 일치하지 않아 무시된다.
일반 `Store::save()`도 메타데이터 테이블이 있다면 해당 행의 오래된 기록을 제거해야 한다.

### 저장 작업 인터페이스

```rust
struct JobKey {
    document_id: DocumentId,
    session_epoch: SessionEpoch,
    request_id: RequestId,
}

struct RecoveryRequest {
    key: JobKey,
    document_revision: u64,
    edit_state_id: EditStateId,
    snapshot: Document,
    metadata: RecoveryMetadata,
}
```

요청은 UI 스레드에서 서로 일치하는 그림과 상태, 경로 정보를 한 번에 캡처한다.
작업자는 GUI와 활성 탭을 읽지 않는다. 작업 결과에도 JobKey와 실제 커밋한 세대·상태를 넣는다.
성공 응답은 DB 커밋 뒤 보낸다. 큐에 넣은 시점을 저장 완료로 표시하지 않는다.
진행 중 스트로크는 확정된 경계에서만 제출한다. 기존 제출 주기를 실시간 내구성 보장으로 설명하지 않는다.

초기 작업자는 하나다. 문서별 최신 복구 요청 하나와 전체 실행 중 요청 하나를 보관한다.
문서별 대기 순서는 순환하고 한 문서의 반복 수정이 다른 문서를 무한히 굶기지 않게 한다.
원본 저장과 닫기에 필요한 작업은 먼저 처리하되 연속 우선 작업 수를 제한한다.
대기 복구 요청의 합치기는 같은 문서에서만 한다. 이미 실행 중인 DB 커밋을 중간에 취소하지 않는다.
전체 스냅샷이므로 대기 중 구세대는 최신 것으로 바꿀 수 있다. 미래 변경분 로그에 이 규칙을 그대로 적용하지 않는다.

열린 문서 수에 따라 SQLite 연결도 제한한다. 처리 대상의 연결만 열고 트랜잭션을 탭 대기 동안 붙들지 않는다.
닫은 문서의 큐는 제거하고 진행 작업은 명시적인 완료 장벽으로 정리한다.
작업자 panic, 채널 종료와 파일 오류는 해당 문서의 실패 상태로 전달한다. 다른 문서의 완료 상태를 올리지 않는다.

### 두 저장소 사이의 순서

복구 DB와 세션 DB는 하나의 원자 트랜잭션이 아니다. 다음 순서를 고정한다.

1. 문서 ID를 만들고 세션 DB에 open, recoverable=false 행을 커밋한다.
2. 초기 복구 스냅샷과 메타데이터를 문서 DB에 커밋한다.
3. 성공 응답을 확인하고 세션 DB에 recoverable=true와 마지막 세대를 커밋한다.
4. UI에 복구 저장 완료를 표시한다.

아직 편집하지 않은 빈 새 문서는 메모리에만 두고 위 등록을 유예한다.
첫 실제 편집이 확정되거나 명시적인 원본 저장에 성공하면 등록과 초기 복구를 시작한다.
등록 실패 시 그림은 메모리에 유지하되 복구 실패와 재시도를 제공한다. 이전 복구 저장 완료 상태를 가져다 쓰지 않는다.
파일에서 연 문서와 내용이 있는 가져오기 문서는 처음부터 등록 대상이다.

3번 전에 종료돼도 open 행의 복구 DB를 직접 검사해 유효한 커밋이 있으면 복구한다.
세션 DB의 마지막 세대는 힌트다. 그것보다 새 유효 DB 커밋을 버리지 않는다.
파일에서 연 문서의 초기 복구가 실패하면 원본 경로 힌트로 다시 열 수 있음을 알린다.
원본 없는 문서의 초기 저장 실패는 복구 실패로 계속 표시한다. 내구성이 생긴 것처럼 표시하지 않는다.

탭 순서와 활성 문서는 전환 뒤 지연 저장할 수 있지만 새 문서 등록과 닫기 결정은 즉시 커밋한다.
앱 실행 시 clean_shutdown=false를 커밋한 뒤 편집을 허용한다.
직전 clean 값은 메모리에 보관해 복원 정책을 결정한다.
세션 DB가 손상됐거나 미지원 버전이면 이 갱신도 하지 않는다.
기존 데이터 위치를 보존한 채 별도 데이터 위치를 선택하기 전까지 자동 복구 기록과 편집을 시작하지 않는다.

| open 행, 복구본과 원본 모두 읽기 실패 | 오류 항목을 남기고 건너뛰기·위치 찾기 제공 |
| 정상 종료, 열려 있던 저장 문서 | 검증한 원본에서 다시 열기 |
| 정상 종료, 열려 있던 미저장 문서 | 보관한 복구 그림을 사용하고 4단계 원본 검증 |
| 정상 종료, 원본을 읽을 수 없고 보관 복구본 유효 | 미연결 복구 문서로 열고 안내 |
| closed 또는 discarded 행 | 자동으로 열지 않음 |
| 새 형식 세션 DB | 자동 재기록 금지, 읽을 수 있는 원본 수동 열기 제공 |

한 문서 실패로 다른 문서 복원을 중단하지 않는다. 실패를 빈 새 그림으로 조용히 대체하지 않는다.
메모리나 탭 한도를 넘는 복원 항목은 닫거나 삭제하지 않고 대기 목록으로 남긴다.
활성 문서 복원이 실패하면 앞선 성공 문서, 없으면 빈 작업 화면을 선택한다.

세션 DB가 손상되면 자동 덮어쓰기와 복구 디렉터리 자동 열기를 하지 않는다.
백업과 진단을 보존하고 별도 수동 복구 화면에서 후보를 제시한다.
버린 문서인지 판별할 수 없는 고아 파일은 사용자가 선택하기 전에는 열지 않는다.
이 규칙으로 세션 목록 손상 때문에 명시적으로 버린 작업이 자동 부활하는 것을 막는다.

### 기존 단일 복구 파일 이전

1. 기존 `recovery.parfait`를 읽기 전용으로 검사한다.
2. 최초 migration_key와 새 문서 ID를 세션 DB에 prepared로 기록한다.
3. 선택한 유효 그림을 새 문서 DB에 기록하고 다시 읽어 검증한다.
4. 세션 open 등록과 migration committed를 한 세션 트랜잭션으로 기록한다.
5. 기존 파일은 자동 삭제하지 않고 이전 백업으로 남긴다.

중단 뒤에는 같은 target_document_id로 이어가며 복구 탭을 중복 생성하지 않는다.
기존 파일이 손상됐거나 미래 버전이면 그대로 남기고 오류를 표시한다.
기존 `before-open.parfait`와 `before-new.parfait`는 자동 탭으로 가져오지 않는다.
별도 수동 복구 대상으로 남기며 새 문서마다 동일 이름의 백업을 만들지 않는다.

### 완료 검사

- [ ] A와 B의 저장 제출이 서로를 덮어쓰지 않는다.
- [ ] 저장 완료 순서가 바뀌어도 해당 문서의 완료 상태만 바뀐다.
- [ ] 메타데이터만 손상되면 그림이 복구되고 연결은 None이다.
- [ ] 최신 그림 손상 시 이전 그림과 이전 메타데이터가 함께 선택된다.
- [ ] 두 DB의 각 커밋 사이에서 프로세스를 강제 종료해 다시 연다.
- [ ] 저장 중 탭 닫기와 같은 경로 재열기에서 이전 epoch 응답을 버린다.
- [ ] 단일 복구 파일 이전의 모든 중단 지점을 재실행해도 원본과 그림이 남는다.
- [ ] 한 문서의 디스크 오류와 복원 실패가 다른 문서를 막지 않는다.
- [ ] 지원하지 않는 버전, 상대 경로, 경로 크기 초과와 잘못된 ID를 거절한다.

## 4단계 원본 연결과 저장 기준

### 연결과 기준 자료

```text
ProjectBinding
  absolute_path
  normalized_path_key
  binding_epoch
  observed_source_head
  overwrite_confirmation_required

SavedBaseline
  edit_state_id                optional
  logical_digest_version
  logical_digest
  source_head
```

`source_head`는 검증한 파일 형식, 선택된 스냅샷의 실제 행 번호와 checksum으로 만든다.
파일 크기와 mtime만으로 동일 원본이라고 판단하지 않는다.
OS 파일 ID는 경로 교체 감지에 보강할 수 있지만 경로가 같은 파일의 내용 검증을 대신하지 않는다.
이 자료는 source_path와 원자적으로 성공한 원본 저장 결과를 묶는다.

### 편집 상태 식별

`EditStateId`는 실제 그림 변경이 확정될 때 새로 만든다.
History Entry와 Pending은 그 상태 ID를 함께 가진다. Undo와 Redo는 기존 ID를 복원한다.
원본 저장 기준은 저장한 ID를 기억한다. 저장 상태로 Undo하면 미저장 표시가 사라진다.
기존 History 숫자 ID와 revision을 영속 상태 ID 대신 사용하지 않는다.

레이어 선택, 뷰와 탭 이동은 revision을 바꾸더라도 새 EditStateId를 만들지 않는다.
선택 범위, 레이어 메타데이터, 픽셀과 마스크 변경은 만든다.
저장에 따른 `Document.name` 동기화는 새 EditStateId나 History 항목을 만들지 않는다.
Undo/Redo로 그림 상태를 복원해도 현재 저장 파일명에 맞춘 문서 이름을 과거 이름으로 되돌리지 않는다.
no-op은 ID와 redo를 유지한다. History 밖에서 그림을 바꾸는 경로도 같은 상태 전환을 거쳐야 한다.
1단계에서 계산을 바꾸지 않고, 이 단계에서 History의 상태 ID 전달과 직접 변경 경로를 감사한다.

런타임의 `same_edit_state()`는 공유 버퍼 동일성 비교로 계속 사용할 수 있다.
현재 이 함수에 포함된 문서 이름 비교는 상태 식별 기반 구현 때 제외해, 이름 동기화만으로 실제 편집이나 redo 폐기로 판정하지 않게 한다. 레이어 이름 비교는 유지한다.
서로 따로 읽은 그림의 픽셀 Arc 주소를 재시작 후 동일성 검사에 사용하지 않는다.

### 영속적인 내용 해시

원본과 복구본의 독립적인 읽기를 비교하기 위해 `ArtDigestV1`을 정의한다.
고정된 순서와 길이, 정수 인코딩을 쓰는 별도 canonical encoder로 SHA-256을 계산한다.
현재 전체 payload checksum은 revision과 활성 레이어도 포함하므로 이 역할로 재사용하지 않는다.

| 포함 | 제외 |
| --- | --- |
| 크기 | Document.name, revision, active, next_layer_id |
| 레이어 순서, ID, 종류, 부모, 역할과 편집 속성 | 뷰, 탭, 레이어 체크와 접힘 |
| 래스터 RGBA의 모든 바이트 | 파일 경로, 세션 ID, 저장 시각 |
| 마스크 유무와 활성화, 커버리지 | 렌더·선택 경계·미리보기 캐시 |
| 선택 범위 유무와 커버리지 | History와 작업 대기열 |

`Document.name`은 파일명에 맞추는 파일 관리 메타데이터이므로 그림 내용 해시에서 제외한다.
그림 내용이 같으면 저장 파일명이나 문서 이름만 달라도 같은 digest다. 레이어 이름 등 그림의 편집 속성은 계속 포함한다.
v9 payload에는 문서 이름을 그대로 저장하고 전체 payload checksum도 이를 검증한다. 내용 동치 비교에서만 제외하며 파일 무결성 검사를 약화하지 않는다.

픽셀은 투명 부분의 RGB까지 포함한다. 문자열은 UTF-8 원래 바이트를 길이와 함께 넣는다.
실수는 검증 후 고정 비트 표현을 사용하며 0과 -0은 같은 값으로 정규화한다.
Uniform과 같은 값을 반복한 Dense 커버리지는 같은 논리 스칼라 스트림으로 해시한다.
선택 None과 Uniform 0은 구분한다. 선택 None과 명시적인 전체 선택도 구분한다.
버전과 도메인 표식을 해시에 포함하고 필드 추가 때 digest 버전을 올린다.

해시는 읽기·저장 작업자에서 계산한다. pointer-move와 매 프레임 미저장 표시를 위해 전체 픽셀을 스캔하지 않는다.
처음에는 파일을 읽은 결과와 원본 저장 요청의 불변 스냅샷에서 계산한다.
digest는 상태 연결의 보조 수단이지 원본 출처의 보안 인증은 아니다.

### 복구 뒤 원본 연결 알고리즘

1. 유효한 복구 그림과 그 세대의 선택적 메타데이터를 읽는다.
2. 경로가 없거나 현재 OS에서 해석할 수 없으면 미연결로 끝낸다.
3. 앱 내부 파일과 중복 연결 대상인지 검사한다.
4. 원본을 읽기 전용으로 열고 버전, checksum과 문서 유효성을 검증한다.
5. 성공하면 경로를 연결하고 읽은 원본의 digest와 source_head를 저장 기준으로 삼는다.
6. 원본과 복구 그림 digest가 같으면 복구 그림의 EditStateId를 저장 기준 ID로 삼는다.
7. 다르면 미저장 상태로 둔다. 복구 메타데이터의 기준 ID는 검증한 원본 digest와 일치할 때만 인정한다.
8. 복구 그림은 원본 그림으로 교체하지 않는다. 임시 원본 픽셀은 비교 뒤 해제한다.

미지원 버전, 파일 없음, 권한 거부, 손상과 빈 DB를 포함한 읽기 실패에서는 `binding=None`, `saved_baseline=None`이다.
일부 검사만 성공했다는 이유로 경로를 활성 연결하지 않는다.
실패한 경로는 진단 메시지나 일회성 위치 찾기 제안으로 표시할 수 있지만 활성 연결로 다시 저장하지 않는다.
원본에서 새로 읽은 내용이 과거 저장 기준과 다르면 외부 변경 안내를 남긴다.
그 상태에서 복구 그림을 저장하려면 외부 변경 확인 정책을 적용한다.
이 경우 `overwrite_confirmation_required=true`로 둔다. 새로 관측한 source_head를 기준으로 삼았다는 이유로 확인을 생략하지 않는다.
이전 기준이 없어 외부 변경 여부를 판단할 수 없고 원본과 복구 그림이 다를 때도 같은 확인을 요구한다.
명시적인 덮어쓰기 승인은 승인한 source_head에만 유효하다. 다시 바뀌면 재확인한다.

### 미저장 표시

| 상태 | 표시 |
| --- | --- |
| 새 빈 문서, 실제 편집 없음 | 원본 없음, 닫을 때 확인 생략 |
| 원본 없는 편집 문서·복구 문서 | 파일 저장 필요 |
| 원본 연결, current ID와 saved ID 동일 | 파일 저장됨 |
| 원본 연결, current ID와 saved ID 다름 또는 기준 ID 불명 | 파일 수정됨 |
| 복구 커밋만 완료 | 위 원본 표시는 유지하고 복구 저장됨 별도 표시 |
| 원본 또는 복구 작업 실패 | 대상과 실패 종류를 분리 표시 |

이미지 가져오기 등 내용이 있는 미연결 문서는 편집 이력이 없더라도 파일 저장 필요다.
새 빈 문서의 판정은 생성 시 상태와 실제 편집 여부로 한다. 흰 픽셀인지 매번 검사하지 않는다.

### 일반 저장과 다른 이름으로 저장

한 문서에서 수동 저장은 동시에 하나만 실행한다. 진행 중 Save As는 비활성화한다.
다른 탭은 편집·전환할 수 있다. 같은 대상 경로에는 문서가 달라도 쓰기를 동시에 수행하지 않는다.

1. 진행 중 편집을 마무리하고 대상 문서, epoch와 binding epoch를 고정한다.
2. 새 경로면 사용자 선택과 덮어쓰기 확인을 받고 중복 경로를 예약한다.
3. 그림, EditStateId와 요청 ID를 불변 저장 요청으로 캡처한다. 후보 스냅샷의 `Document.name`은 저장 대상 파일의 확장자를 제외한 이름으로 맞추되 현재 세션은 아직 바꾸지 않는다.
4. 외부 변경 확인이 필요한 연결은 먼저 승인을 받는다. 작업자가 대상 파일의 source_head를 다시 확인하고 승인 이후 변경이 있으면 쓰기 전에 멈춘다.
5. 기존 v9 그림과 연결된 선택적 원본 상태 메타데이터를 같은 DB 트랜잭션으로 기록한다.
6. 커밋 성공 응답의 상태 ID를 저장 기준으로 삼는다. 현재 문서가 더 수정됐으면 수정 표시는 남는다.
7. 커밋 성공 뒤 해당 세션의 `Document.name`을 후보 이름으로 맞춘다. Save As의 새 연결도 이때 반영하고 binding epoch를 올린다. 저장 중 추가된 그림 편집은 덮어쓰지 않는다.
8. 갱신된 연결과 저장 기준을 담은 복구 요청, 세션 경로 힌트 갱신을 제출한다.

원본에는 다음 선택적 테이블을 둔다. 경로와 문서 세션 ID는 원본에 저장하지 않는다.

```text
project_metadata
  generation                 primary key
  snapshot_checksum
  metadata_version
  edit_state_id
  logical_digest_version
  logical_digest
  metadata_checksum
```

checksum은 앞선 필드 전체를 고정 인코딩으로 묶는다. 메타데이터 행 하나는 최대 1 KiB다.
원본의 선택적 메타데이터도 실제 스냅샷 행과 checksum에 묶고 누락돼도 그림을 읽을 수 있게 한다.
그림과 같은 트랜잭션으로 쓰고 보관된 그림 세대와 함께 정리한다.
읽은 원본 digest를 직접 계산한 결과와 일치할 때만 사용한다. 자체 digest 선언만 믿지 않는다.
기존 디스크 revision보다 큰 저장 세대가 필요하면 디스크용 복사본만 조정한다.
성공 응답을 현재 메모리 revision으로 바꾸어 저장 완료 범위를 넓히지 않는다.
Save As 실패나 파일 선택 취소는 기존 이름, 경로와 저장 기준을 유지한다. 예약 경로는 작업 종료 때 해제한다.

SQLite 커밋 전 실패와 커밋 후 checkpoint 실패를 구분한다.
커밋이 성공했다면 해당 그림은 원본 저장 기준으로 인정하고, checkpoint 오류는 별도 마무리 경고와 재시도로 처리한다.
checkpoint가 끝나기 전 단일 파일만 복사해도 안전하다고 안내하지 않는다. 유효한 WAL과 복구본을 임의 삭제하지 않는다.
원본 성공 뒤 복구 메타데이터 갱신이 실패해도 원본 저장을 실패로 되돌리지 않는다.
복구 실패 경고를 유지하고 재시도한다. 재시작 때는 원본을 다시 검증하므로 오래된 경로 힌트만 믿지 않는다.

외부 프로그램과의 강한 compare-and-swap 파일 쓰기는 이번 범위의 보장이 아니다.
앱 내부 예약과 협력 잠금, 쓰기 전 검증으로 관측한 충돌을 막고 남은 외부 교체 경합은 한계로 명시한다.
오래된 디스크 상태를 덮어쓰는 확인은 후속 닫기 확인과 별개이며 이번 범위에 포함한다. 확인 없이 외부 변경을 덮지 않는다.

## 이번 범위의 닫기와 종료 안전 정책

저장·저장하지 않음·취소 확인 UI와 그 결정 처리는 후속으로 미룬다. 이를 확인 없는 버리기로 대체하지 않는다.

- 문서 닫기는 진행 중 편집을 확정한 뒤 원본 저장 상태를 판정한다. 원본에 저장된 문서와 아직 편집하지 않은 빈 새 문서에만 허용하고, 미저장 문서는 탭을 유지하고 수동 저장을 안내한다.
- 허용된 닫기와 앱 종료를 처리하는 동안 대상 문서의 새 편집과 저장 제출을 막는다. 실패로 중단하면 차단을 풀고 문서를 유지한다.
- 허용된 닫기는 대기 복구 요청 제거와 실행 중 작업의 완료 장벽 뒤 세션 DB에 closed를 커밋한다. 성공한 뒤에만 탭을 제거하고 복구 디렉터리를 정리한다.
- 닫기 커밋 실패 시 문서를 유지한다. 삭제 실패 시 closed 행을 tombstone으로 남기고, 정리 대기 상한 32개를 적용한다.
- 앱 종료는 원본 저장 선택을 묻지 않는다. 모든 진행 중 편집을 확정하고 최종 복구와 작업 종료 장벽을 완료한 뒤, 미저장 문서를 포함한 탭을 open으로 보관한다.
- 편집하지 않은 빈 새 문서만 복원 대상에서 제외한다. 원본 저장과 복구 저장 상태를 구분한 채 세션 기록과 clean_shutdown=true를 한 트랜잭션으로 커밋한다.
- 최종 복구나 세션 커밋에 실패하면 종료를 중단하고 오류를 표시한다. OS 강제 종료는 마지막 유효 커밋까지만 복구한다.
- 정상 재시작에서도 미저장 문서는 복구본을 사용하며 원본으로 교체하지 않는다. 저장된 문서는 기존 정상 재시작 정책을 따른다.

### 완료 검사

- [ ] 저장 상태에서 편집, Undo, Redo를 하면 원본 수정 표시가 맞는다.
- [ ] 별도로 읽은 동일 그림은 같은 digest이며 active와 revision만 달라도 같다.
- [ ] `Document.name`과 저장 파일명만 달라도 digest는 같고, 레이어 이름이 다르면 digest가 다르다.
- [ ] Save As 성공 시 메모리와 원본의 문서 이름이 저장 파일명에 맞으며, 실패·취소 시 기존 이름과 연결을 유지한다.
- [ ] 저장 이름 동기화는 편집 상태 ID와 redo를 유지하고, Undo/Redo가 현재 파일명에 맞춘 문서 이름을 되돌리지 않는다.
- [ ] 픽셀·마스크·선택·폴더 메타데이터의 차이는 digest가 다르다.
- [ ] 복구본의 원본 없음, 손상, 권한 거부, 미래 버전에서 그림은 남고 연결은 None이다.
- [ ] 원본이 외부에서 바뀌면 복구 그림을 바꾸지 않고 덮어쓰기 확인을 요구한다.
- [ ] 저장 중 더 그린 뒤 이전 상태의 저장 완료가 와도 수정 표시가 남는다.
- [ ] A의 Save As가 끝나는 동안 B로 전환해도 A의 연결만 바뀐다.
- [ ] 원본 커밋 실패와 checkpoint 실패, 복구 갱신 실패를 서로 다르게 처리한다.
- [ ] 저장된 열린 탭은 정상 재시작에 원본, 비정상 재시작에 복구본 우선으로 복원한다.
- [ ] 확인 흐름 구현 전에는 미저장 문서 닫기를 차단하고 수동 저장을 안내한다.
- [ ] 확인 흐름 구현 전에는 앱 정상 종료 뒤에도 미저장 탭을 복구본에서 복원한다.

## 후속 구현: 문서 닫기와 앱 종료의 확인 흐름

이 절은 후속 설계 초안이며 이번 1~4단계의 구현·완료 기준에 포함하지 않는다.
저장·저장하지 않음·취소 선택, 닫기 중 원본 저장, 앱 종료 결정 수집과 명시적 버리기를 이후에 구현한다.
아래 동작은 후속 구현이 완료된 뒤 적용하며, 그 전에는 앞 절의 임시 안전 정책을 따른다.

### 문서 수명 상태

```text
Open
  -> AskingClose
  -> SavingForClose
  -> DrainingJobs
  -> CommittingClose
  -> Closed

AskingClose -> Open                 cancel
SavingForClose -> AskingClose       failure or save-dialog cancel
DrainingJobs -> AskingClose         failure
CommittingClose -> AskingClose      session commit failure
```

닫기 처리를 시작하면 대상 문서의 새 편집과 저장 제출을 막는다.
다른 문서 편집은 허용한다. 앱 전체 종료를 묻는 동안에는 모든 대상 문서를 동결한다.
저장된 문서와 아직 편집하지 않은 빈 문서는 확인 없이 DrainingJobs로 간다.
나머지는 저장, 저장하지 않음, 취소를 제공한다. 미연결 문서의 저장은 파일 선택으로 이어진다.
파일 선택 취소와 저장 실패는 문서를 제거하지 않는다.

### 닫기 확정 순서

1. 필요한 원본 저장을 끝내거나 사용자의 저장하지 않음 결정을 받는다.
2. 문서의 대기 복구 요청을 제거하고 실행 중 작업의 종료 장벽을 기다린다.
3. 세션 DB에 closed 또는 discarded를 커밋하고 탭 순서와 활성 문서를 함께 갱신한다.
4. 커밋 성공 뒤 메모리 세션과 경로 예약을 제거한다.
5. 닫힌 문서의 복구 디렉터리는 후속 정리로 삭제한다.

2번 전 실행 중이던 저장이 끝나도 닫기 결정을 되돌리지 않는다.
3번 전 실패하면 탭과 그림을 유지하고 작업 재개 또는 닫기 재시도를 제공한다.
3번이 닫기의 커밋 지점이다. 그 뒤 늦은 성공 응답은 열린 문서를 다시 만들 수 없다.
정리 실패는 파일이 남았다는 경고이며 닫기 결정은 유지한다.
세션 행은 복구 디렉터리 삭제를 확인한 뒤에만 제거한다. 그 전에는 tombstone 역할을 한다.
정리 실패가 반복돼 레코드와 디스크 사용이 끝없이 늘지 않도록 남은 정리 항목은 32개로 제한한다.
상한에서는 새 문서 등록을 막고 정리 재시도나 데이터 위치 변경을 안내한다. 그림을 자동 삭제하지 않는다.

### 앱 전체 종료

앱 종료는 탭을 하나씩 즉시 닫는 동작과 다르다.

1. 모든 진행 중 편집을 확정하고 대상 문서 목록을 고정한다.
2. 탭 순서대로 필요한 저장 결정을 모은다. 이 동안 탭 제거와 복구 삭제는 하지 않는다.
3. 저장을 선택한 문서의 원본 기록을 완료한다. 실패하면 종료를 멈추고 해당 문서를 보여 준다.
4. 취소하면 문서 동결을 풀고 종료를 철회한다. 이미 성공한 원본 저장은 되돌리지 않는다.
5. 모든 결정이 끝나면 유지할 문서의 최종 복구와 모든 작업의 종료 장벽을 완료한다.
6. 한 세션 트랜잭션으로 저장된 탭의 open 기록과 순서를 남기고 버린 문서는 discarded로 기록한다. 등록된 빈 새 문서도 복원 대상에서 제외한다.
7. 같은 트랜잭션에서 clean_shutdown=true를 기록한 뒤 실제 창을 닫는다.
8. 버린 문서와 편집하지 않은 빈 문서만 후속 정리한다. 저장된 열린 탭의 복구본은 다음 원본 검증까지 보관한다.

정상 종료 뒤 복원할 저장 문서는 open 행으로 남는다. 이는 사용자 탭 닫기의 closed와 다르다.
모든 작업과 세션 기록이 끝나기 전에 앱 전체 clean을 기록하지 않는다.
문서 DB의 clean과 앱 전체 clean은 별개다. 문서 하나가 clean이어도 앱 전체 종료 완료를 뜻하지 않는다.
마지막 세션 커밋 실패는 종료를 중단한다. 실패한 실행을 정상 종료로 표시하지 않는다.
OS 강제 종료는 취소할 수 없으므로 마지막 유효 커밋까지만 복구한다.

복구 실패 문서를 계속 닫으려면 원본 저장 성공 또는 명시적인 저장하지 않음이 필요하다.
오류를 이유로 자동으로 버리거나 실패한 최신 복구본을 정상 저장으로 표시하지 않는다.

### 후속 완료 검사

- [ ] 문서 닫기와 앱 종료에서 저장, 저장하지 않음, 취소를 처리한다.
- [ ] 닫기 저장·버리기·취소와 파일 선택 취소, 저장 실패를 검사한다.
- [ ] 앱 종료 중 세 번째 문서에서 취소해도 앞 문서의 탭과 그림이 남는다.
- [ ] 버리기 확정 뒤 강제 종료와 삭제 실패에서도 자동 복원이 일어나지 않는다.

## 테스트 가능한 커밋 단위

1~4단계는 기능의 책임 구분이다. 실제 커밋은 아래 검증 경계로 나눈다.
단계별 커밋 표의 각 행은 구현과 해당 테스트를 함께 넣는 커밋 하나다. 선행 커밋 위에서 빌드하고 검사할 수 있어야 하며, 모든 커밋이 각각 배포 가능한 기능일 필요는 없다.
아래 번호와 테스트 이름은 구현 계획이다. 완료로 표시한 단위만 구현·검증했으며 나머지는 현재 동작을 뜻하지 않는다.

### 기능 검증과 효과 검증

- **기능 검증**: 사용자의 명령과 상태 전이가 명세대로 동작하는지 확인한다. 새 탭, Undo, 저장, 복원과 실패 처리가 대상이다.
- **효과 검증**: 변경 목적이 실제로 달성됐는지 확인한다. 다른 문서에 영향이 없는지, 마지막 유효 그림이 살아남는지, 버퍼와 대기열이 제한되는지, UI 스레드에서 파일 처리가 빠졌는지가 대상이다.
- **회귀 검증**: 바꾸지 않기로 한 픽셀, 기존 파일 읽기, redo와 내구성이 유지되는지 확인한다. 각 커밋의 기능·효과 검증에 함께 포함한다.
- **성능 검증**: 효과가 시간이나 자원 사용에 관한 경우 release workload로 전후를 측정한다. 효과 검증 전부를 속도 벤치마크로 대신하지 않는다.

함수 호출의 성공, 화면의 문구, 테스트 개수 증가만으로 효과를 통과 처리하지 않는다.
그림 바이트, 독립적으로 만든 기대 상태, 실제 재시작 결과, 큐 길이와 고유 버퍼 계수 등 관측 가능한 근거를 남긴다.
동일한 새 digest 함수로 기대값과 결과를 모두 만들고 같다고 확인하는 자기 검증은 피한다.

### 공통 fixture와 실행 방식

| 이름 | 구성과 쓰임 |
| --- | --- |
| A/B | 크기와 LayerId, revision은 같지만 픽셀 패턴과 이름이 다른 작은 문서. 잘못된 대상 라우팅과 캐시 혼합 검출 |
| M | 폴더, 마스크, 분수 선택 커버리지와 투명 RGB가 있는 문서. 원본 바이트와 독립적인 합성 결과 보관 |
| H | 편집 2회, Undo 1회 뒤 redo가 남아 있는 상태. 실패·취소·no-op의 비파괴성 확인 |
| P | 같은 파일명/다른 디렉터리, 유니코드 경로, 읽기 전용·없는·손상·미래 버전 파일. 각 OS에서 가능한 별칭 사례 추가 |
| Q | 실행과 응답 순서, 오류와 완료 장벽을 직접 제어하는 가짜 작업자. sleep에 의존하지 않고 역순·중복·지연 응답 재현 |
| R | 별도 프로세스와 실제 SQLite를 사용하는 중단 지점 fixture. 준비 신호 뒤 kill하고 같은 데이터 위치로 재실행 |
| B | 작은 한도에서 경계를 정확히 넘기는 예산 fixture와 별도 opt-in 대형 release workload. 작은 검사가 최대 RSS 검증을 대신하지 않음 |

공통 fixture는 독립적으로 작성한 테스트 데이터만 쓴다. 실제 사용자 파일과 앱 데이터 디렉터리는 사용하지 않는다.
1A에서 기존 `project_state` 검사, 실제 egui 입력 검사와 `recovery_probe`를 재사용할 부분을 정한다.
새 전용 probe와 가짜 작업자는 해당 검증에 필요한 시점에 추가한다. 프로덕션 저장 경로를 테스트 편의상 우회하지 않는다.

새 검사는 `multi_document_` 접두어로 검색·실행할 수 있게 한다. 다음 명령은 그 이름 규약으로 추가할 검사에 대한 실행 계획이다.

```sh
cargo test -p parfait-core multi_document_
cargo test -p parfait-storage multi_document_
cargo test -p parfait multi_document_
cargo test --release --workspace multi_document_ -- --ignored --nocapture
```

관련 crate의 기존 검사도 함께 실행한다. 필터 결과 0개는 해당 커밋의 검증 성공이 아니다.
실제 프로세스 중단 검사는 기본 통합 검사에 포함하고, 느린 대형 자원·시간 측정만 opt-in으로 둔다.
각 커밋에서 아래 공통 fmt·Clippy·workspace 검사를 통과한다. 비용이 큰 native/release 측정은 아래 지정 커밋에서 수행하고 미실행은 따로 적는다.

### 단계별 커밋 구성

단계별 2~3개, 총 10개 커밋으로 묶는다. 기준선·fixture·검증 도우미만을 별도 커밋으로 떼지 않고 해당 구현과 함께 넣는다.
1A 안에서는 리팩터링 전에 기준선을 먼저 확보한 뒤 변경 후 결과와 비교한다.

### 성능 효과의 판정

1A의 변경 전에 하드웨어, OS, release 옵션, workload/입력/그림 checksum, 샘플 수와 측정 구간을 고정한다.
1A의 단일 문서 리팩터링, 2A의 전환·캐시, 2C의 예산, 4A의 저장 중 입력, 4B의 전체 경로에서 필요한 측정을 반복한다.
시간 비교는 동일 조건의 전후 실행을 최소 3회 교차하고 p50/p95/p99·최댓값과 편차를 남긴다. p99를 해석할 표본이 부족하면 미측정으로 표시한다.

정확성·격리·큐/버퍼 상한은 표의 불변식으로 통과/실패를 판정한다.
시간과 RSS의 회귀 허용치는 1A 기준선의 반복 편차를 보고 변경 전에 항목별로 정해 기록한다. 아직 수치가 없으므로 이 문서에서 임의의 ms나 개선율을 통과 기준으로 만들지 않는다.
허용치를 정하지 않았거나 동일 조건 비교가 없으면 측정값만 기록하고 성능 효과는 미판정으로 남긴다. 기능 검증 통과와 성능 효과 통과를 구분한다.
비활성 탭의 그림 자체가 차지하는 메모리 증가와 불필요한 복제·텍스처 증가를 구분하고, 버퍼 예산을 최대 RSS와 동일시하지 않는다.
UI 작업자 분리는 실행 스레드 관측으로, 실제 입력 프레임 영향은 별도 workload로 검증한다. 물리 펜 지연 개선으로 확대 해석하지 않는다.

계획을 나누는 것만으로 구현 현황이나 테스트 통과 수를 올리지 않는다.
커밋은 이 표의 경계로 나누되 실제 파일명은 책임에 맞게 정한다. 기존 파일과 중복 역할이면 하나로 정리한다.
`Document`와 레이어 종류 추가는 상태 추출 커밋에 섞지 않는다.
새 레이어 자료가 병행 추가되면 기존 v9라는 숫자 대신 실제 합쳐진 그림 버전과 fixture를 기준으로 갱신한다.

### 후속 확인 흐름의 별도 커밋

아래는 이번 1A~4B의 완료 조건에서 제외한다. 기본 닫기·종료 안전성을 확인 UI 구현과 혼동하지 않는다.

| 후속 커밋 | 기능 검증 | 효과·회귀 검증 |
| --- | --- | --- |
| F01 문서 닫기 선택 | 저장·저장하지 않음·취소, 미연결 파일 선택과 선택 취소, 원본 저장 실패 | 취소·실패 시 그림·탭 유지. 저장 성공 또는 명시적 버리기 뒤에만 닫기 커밋 |
| F02 앱 종료 결정 수집 | 여러 탭의 결정 수집, 중간 취소와 저장 실패, 동결 해제 | 세 번째 문서 취소 뒤 앞 탭도 유지. 이미 성공한 원본 저장은 유지하고, 전체 종료 성공 전 clean 기록 없음 |
| F03 명시적 버리기 내구성 | discarded 전이, 정리 실패·상한과 재시도 | 버리기 커밋 뒤 kill/삭제 실패에도 자동 복원 0건. 정상 종료의 저장 탭 복원 회귀 없음 |

## 공통 검증과 기록

### 자동 검사

- [ ] `cargo fmt --all -- --check`
- [ ] `cargo clippy --workspace --all-targets -- -D warnings`
- [ ] `cargo test --workspace`
- [ ] 기존 그림 버전 fixture와 손상 세대 복구 검사 유지
- [ ] 앱 데이터 디렉터리는 테스트마다 별도 임시 위치 사용
- [ ] 저장 순서와 실패 지점을 주입하는 결정적인 가짜 작업자 검사
- [ ] 별도 프로세스를 종료해 실제 SQLite 커밋 경계 복구 검사

### 실패 주입

원본 열기 전, 그림 커밋 전후, 메타데이터 기록, 세션 갱신 전후, 닫기 커밋 전후와 삭제 사이를 나눈다.
각 지점에서 강제 종료, 디스크 쓰기 실패와 읽기 실패를 주입한다.
최신 유효 그림 유지, 다른 문서 독립성, 닫힌 문서 비복원, 구형 원본 보존을 함께 확인한다.
명시적 버리기 비복원 검사는 후속 확인 흐름 구현 때 추가한다.
작업자 응답은 중복·역순·닫힌 epoch·존재하지 않는 문서 ID를 넣어 검사한다.
트랜잭션 성공을 모르는 상태에서 같은 요청을 재시도해도 별도 문서나 연결을 중복 생성하지 않는다.

### 실제 화면과 성능

작은 그림 3개, 최대 허용 메모리에 가까운 그림, 같은 이름의 다른 경로, 폴더·마스크·선택 문서를 사용한다.
탭 전환, 긴 스트로크, 이름 편집과 모달, 저장 중 편집, 미저장 닫기 차단, 정상 종료 뒤 미저장 탭 복원과 강제 종료를 확인한다.
저장·저장하지 않음·취소 선택과 종료 취소는 후속 확인 흐름 구현 때 검사한다.
Windows, macOS와 Linux의 경로·파일 잠금·읽기 전용 원본·SQLite 보조 파일 처리를 각각 확인한다.
펜 입력 검증과 마우스 UI 검증을 구분한다. 확인하지 않은 플랫폼을 검증 완료로 적지 않는다.

단일 문서 기준과 비교해 입력 프레임 p50/p95, 탭 전환 시간, 저장 시간, 저장 대기 시간과 최대 RSS를 기록한다.
같은 release 빌드 조건과 그림 checksum을 사용하고 인코딩 CPU 시간과 끝까지의 저장 시간을 나눠 적는다.
작업자 하나와 전체 스냅샷 유지로 생기는 대기·메모리 한계는 성능 기록에 남긴다.
이번 범위에서 변경분 저장이나 물리 펜 지연 개선을 완료했다고 주장하지 않는다.

검증 절차는 [검증 기록](testing.md), 측정 형식은 [성능 기록](performance.md)을 따른다.
완료된 묶음만 [구현 현황](status.md)과 [프로그램 구조](architecture.md)에 반영한다.
타일·청크 저장과 변경분 복구는 이 계획의 상태 ID와 저장 인터페이스를 사용하되 별도 포맷 명세로 진행한다.
